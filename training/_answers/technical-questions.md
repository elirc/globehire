# SEALED: technical questions (reference answers)

1. **Singleton handler.** Every dependency, transitively, must be singleton-safe: thread-safe, and holding no per-request or per-user state. Today they're singleton repositories, `IClock` and `IIdGenerator`, so it's *currently* safe. Incident 001 shows the future problem: the next PR adds a scoped dependency and nobody rechecks the lifetime. Enforce it with `builder.Host.UseDefaultServiceProvider(o => { o.ValidateScopes = true; o.ValidateOnBuild = true; })` in all environments, plus a test that builds the provider. Also question the premise: six small allocations per request aren't a measured bottleneck (p95 in incident 001 barely moved).

2. **Captive dependency.** A singleton is constructed once, from the root provider. Its scoped dependencies are resolved from the root scope too, so they live as long as the app. ASP.NET Core enables `ValidateScopes`/`ValidateOnBuild` only when the environment is Development, where startup is expected to throw. `WebApplicationFactory` fixtures that call `UseEnvironment("Testing")` skip it, so the tests run a container that silently allows the capture.

3. **Start date.** It's a *calendar date in the hiring country* (a contract says "starts 15 July", which means 15 July in New York). The guard must compare it with *today in that country*, not the UTC date. Smallest change: `IClock.TodayIn(CountryCode)`, which converts the **instant** `UtcNow` to the country zone and then takes the date (`TimeZoneInfo.ConvertTime(UtcNow, zone).DateTime`). Use it in *both* `CreateWorkforcePlanHandler` and `ActivateEmploymentHandler`. The zone should come from the country policy data, not a hard-coded map.

4. **Time tests.** For a west zone (US) and an east/DST zone (GB): mid-day local; 1 minute before local midnight; exactly local midnight; the window between UTC midnight and local midnight in each direction; a DST-switch day; winter vs summer; an unconfigured country (fallback). Each one sits on a different boundary. `IClock` lets the test pin the instant deterministically. With `DateTime.UtcNow` the result depends on when CI runs, so the bug shows up as a flaky test at 8 pm Eastern.

5. **Hire-case lost update.** Requests A and B both read the case at version 3, and both call `CompleteTask(..., 3)`. Both pass `EnsureVersion` before either increments, and both increment, giving version 5 with both believing they won. (Or `_tasks[index] = …` races on the `List<T>`.) In SQL: `UPDATE HireCases SET …, Version = Version + 1 WHERE ClientId = @c AND Id = @id AND Version = @expected;`, where 0 rows affected means a conflict. The check and the write become one atomic statement.

6. **EF Core.** The `lock` only ever protected one process. It's gone with a database, and it was wrong with two replicas anyway. Use an EF Core concurrency token: a `rowversion` column (`[Timestamp]`/`IsRowVersion()`) or `Version` configured with `IsConcurrencyToken()`. `SaveChanges` adds `WHERE Version = @original` and throws `DbUpdateConcurrencyException` on 0 rows, which maps to **412 Precondition Failed** when the client sent `If-Match`. Keep the domain `EnsureVersion` for the in-process check. The database check is the one that holds across replicas.

7. **One live offer per hire case.** A unique index on `(ClientId, HireCaseId)` (filtered to live statuses if cancelled offers can exist), with the violation (`SqlException` 2601/2627) mapped to `409`, or to returning the existing offer if the request is idempotent. A handler check alone is check-then-act: two concurrent requests both see "no offer" and both insert. Only the database sees both writes.

8. **Idempotency.** Store `(ClientId, Key) → (request fingerprint, e.g. a SHA-256 of the canonical body, + stored response/status + resource id)`. A replay with the same fingerprint returns the stored response. A different fingerprint is a client bug, so return **422** (or 409) with `idempotency_key.reused_with_different_request`. Never silently return the old resource. Keys need a retention window.

9. **Error contract.** `concurrency.version_mismatch` should be **412 Precondition Failed** (stale `If-Match`). `concurrency.if_match_required` should be **428 Precondition Required**. Genuine validation stays 422, and a not-found case is 404. When everything is 422, a client can't tell "reload and retry" from "your input is wrong" without string-matching `code`. Generic retry policies and gateways treat 422 as permanent, so a harmless conflict becomes a user-facing failure.

10. **Rescue order.** Start with characterization tests that pin current behaviour: the hire-case happy path, a stale-version rejection, and a two-writer race test that *fails* (it documents the bug). Then the calendar boundary table, which fails on the US daytime rows. Then fix one at a time, in small diffs. (a) Add `MutateAsync(ClientId, Guid, Action<HireCase>)` to `IHireCaseRepository` and route `CompleteTaskAsync`/`SubmitAsync` through it, mirroring offers (about 20 lines, no domain change). (b) Add `TodayIn` converting the instant, used by both guards. Separate PRs, each with its own red → green test. No refactoring beyond what each fix needs.
